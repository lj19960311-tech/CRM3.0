# 01 Agent 架构与工程规范

# 架构总览与 Agent Loop

三层结构，单 Agent 统一入口：

|层|职责|说明|
|---|---|---|
|规划层（Main Agent）|理解目标、意图识别、任务拆解、调度执行、整合结果<br>|单点请求直达工具；复合任务生成任务计划（对用户可见、逐步点亮）|
|技能层（Skill）|业务方法论容器：客户分析、产品匹配、案例匹配、知识应用、CRM 更新等|Skill 间是上下文累积，不是结果拼接<br>|
|工具层（Tool）|确定性数据进出，无推理：工商查询、产品库、车辆平台、知识库检索、CRM 读写|旧「快捷功能」全部下沉至此层|



**数字人专家 = 呈现层概念。** 前端把 Skill 按业务角色打包为「物流产品专家 / 车辆专家 / 商机管家…」等拟人化入口；底层仍是统一 Main Agent \+ Skill 池，不为每位专家单建 Agent。用户可指定专家发起，也可直接说目标由 Main Agent 自动匹配。



**多业务演进原则：** 拆独立 Agent 的唯一理由是知识库与产品体系硬隔离（金融、生态营销远期各自成 Agent \+ 上层规划编排）。一期 按可被编排的标准 Agent 建（走中台 Enio 标准接口：tool 动态注册、A2A 预留、会话存储、统一知识检索）。



**循环**：**感知**（用户输入 \+ 加载用户/客户上下文）→ **规划**（Planner 判定意图与路径）→ **执行**（按规划调 skill/tool，单步产物入上下文）→ **观察**（产物是否满足下一步，不满足回头或反问）→ **收敛**（达成目标或链路跑完则交付）。

**意图分流**：单点请求（查线索归属/查车/知识问答）→ 直接路由对应 tool，**不走完整规划链**（P95 延迟保障）；复合任务（备访/出方案）→ 规划内核拆工作链，按用户切入点动态裁剪，不强行走全。

**反问澄清四原则**：

①澄清是兜底非默认，能不问就不问 

②带着干好的活去问（先交付概况）

③给选项，不开放式提问 

④用户答不上来的（行业参数）不问，默认值兜底标注，但需用户二次确认。

**硬约束**：单任务步数上限 12（可配，超限输出已有产物）；写操作必须经确认卡；每步工具调用透传用户身份；权限一律在数据服务层校验（Agent 层不做权限判断）。



# Skill 定义规范（SKILL.md 模板）

每个 skill 一个目录，含 `SKILL.md` 与注册元数据。模板：

```Plain Text
---
name: sales_insight            # 唯一名，snake_case
version: 1.0.0
description: >                 # 一句话：何时该用（Planner 路由依据，写"用户想达成什么"）
  用户要为某客户做销售准备/出方案时使用：完成客户分析、产品匹配、案例检索并生成方案报告。
triggers:                      # 触发示例（全部进评测集，≥3 条）
  - "明天要去拜访{客户}，帮我做客户分析并出一版物流产品方案"
inputs:
  - customer_name: string      # 来自用户输入或焦点客户
  - confirmed_profile: object  # 来自画像确认卡（人工确认后）
outputs:
  - plan_report: doc_card      # 结构化输出 schema 引用，前端按此渲染
tools:                         # 只声明用到的 tool，Planner 不得越权调用未声明工具
  - query_biz_info
  - calc_benefit_model
steps:                         # 默认步骤链（Planner 可裁剪）；人工确认点用 ⏸ 显式标注
  1. 客户分析（query_biz_info + query_customer_profile + web_search）
  2. ⏸ 画像确认卡
  3. ⏸ 参数确认卡（行业默认值预填）
  4. 产品匹配（match_product_lib + calc_benefit_model）
  5. 案例检索（search_case_lib）
  6. 生成方案（gen_docx）
fallbacks:                     # 必填，无兜底不予注册（对应各功能 PRD §6）
  - search_case_lib EMPTY → "未找到完全匹配案例"+通用方案，禁止编造
eval:                          # 验收用例（进 L1 评测集）
  - given: "帮鞍山钢铁出方案" expect: 走完 6 步且收益表数字与因子模型一致
---
Plain Text
```

**编写规则**：description 面向"何时用"，≤2 句；steps 确认点必须 ⏸ 标注；fallbacks 必填；triggers 全量进评测集。



# Tool 定义规范

每个 tool 提供 JSON Schema 描述 \+ 实现注册，与中台动态工具注册对齐：

```Plain Text
name: publish_opportunity
type: write                    # read / write；write 类强制走确认卡
description: 将机会信息写入CRM并发布。仅在用户通过确认卡确认后调用。
input_schema:                  # JSON Schema，字段带中文 description（LLM 依此填参）
  customer_name: {type: string, description: 客户全称（消歧后）}
  est_amount: {type: number, description: 预计金额（万元）}
  stage: {type: string, enum: [初次触达, 需求确认, 方案报价, 商务谈判, 签单]}
output_schema:
  receipt_no: {type: string, description: 业务单号}
errors:                        # 必须区分三态（决定 Agent 走兜底还是重试）
  EMPTY: 无结果（业务合法，如案例库查空）
  FAILED: 调用失败（可重试，N=2）
  FORBIDDEN: 无权限（不可重试，透传用户提示）
idempotency: session_id + card_id 作幂等键；重复调用返回原回执
timeout: 8s（读）/ 15s（写）
auth: 透传当前用户身份，权限在数据服务层校验
Plain Text
```

**编写规则**：读写分离（一个 tool 不得同时读写）；写 tool 的 description 必须含"仅在用户确认后调用"；错误三态强制；写 tool 必须配套回执查询接口（超时核对用）。

**Tool 全清单**：query\_biz\_info / query\_customer\_profile / query\_risk / web\_search / kb\_search / query\_vehicle / calc\_finance\_quote / query\_lead\_drop / query\_lead\_owner / query\_drop\_rules / search\_case\_lib / match\_product\_lib / calc\_benefit\_model / gen\_docx / gen\_pdf / gen\_deep\_report / publish\_opportunity / write\_crm\_note

# 技术选型

## 5\.1 Agent 框架：基线 Eino

**结论：Eino 留用。两个****x****自研通用件为工作量重点**：

1. **确认卡断点恢复**：规划链在 ⏸ 节点挂起、状态落库、确认后从断点恢复（对应"规划链中断不从头重跑"）

2. **会话级 checkpoint**：支撑历史完整回放 \+ SSE 断点续传（按消息 id 补发）

# 非功能需求

**性能**：端到端 P95 ≤ 现状×1\.3；用户 3s 内必须看到首个反馈（思考块或计划卡）；可并行工具（查工商\+查画像\+查风险）并行调用；单点直达不过完整规划链。

**安全**：

- 权限：tool 调用透传用户身份，数据服务层校验；记忆销售ID\+客户ID双键隔离；越权用例 0 通过（硬门槛）

- 写安全：写 tool 强制确认卡 \+ 幂等 \+ 回执可查

- 注入防护：外部数据（工商/网页/上传文档）进上下文前清洗与标记（数据不解释为指令）

- 数据合规：模型走云上专属区；日志与评测采样脱敏（客户名/金额/联系方式）；LLM 请求日志保留期与访问权限单独定义

- 审计留痕：每次写操作挂操作人/时间/会话id/卡片快照，只读不可删

**可观察性**：每任务生成 trace（规划决策、每步工具入出参摘要、耗时、token），支撑"销售反馈答错 → 当场定位是哪步哪个工具的问题"。
